# GIF 按时长抽帧与 50 帧上限设计

## 背景

Works 页面上传、像素编辑器导入和远程 GIF 回退解析当前都先完整解码 GIF。编辑器对超过 50 帧的导入或远程作品采取拒绝策略，项目清洗则直接保留前 50 帧；Works 上传没有统一的帧数限制。直接拒绝或截断都会损失可用性，直接截断还会缩短动画总时长。

## 目标

- GIF 最多输出 50 帧，超过时按时间轴等间隔重采样。
- 以每个目标区间的中点选择当时正在播放的原始帧。
- 相邻区间命中同一原始帧时合并，并累加区间延时。
- 标准化后的原总时长与抽样结果总时长严格一致。
- 非法或小于 20ms 的延时统一按 20ms 处理。
- Works 上传和编辑器导入都在 32×16 像素转换前抽样。
- 编辑器从当前帧导入时，抽样上限使用项目剩余容量。
- 保存、导出和设备预览保留最终兜底，保证不会输出超过 50 帧的 GIF。
- 不改变传入 GIF 的 5MB 等现有文件大小规则。

## 共享纯函数

新增 `src/modules/pixel-editor/core/gif-frame-sampling.ts`：

```ts
export function sampleGifFramesByDuration<T extends { delay: number }>(
  frames: T[],
  maxFrames = 50
): T[]
```

函数不修改输入数组或原始帧对象。它返回浅复制帧，保留 `image`、`layers`、`pixels`、`id` 等字段，只更新输出 `delay`。

输入规则：

- 空帧数组抛错。
- `maxFrames` 必须是正整数，否则抛错。
- 延时有限且不小于 20ms 时四舍五入为整数毫秒；其他情况统一为 20ms。
- 即使帧数未超过上限，也返回延时标准化后的副本，不做抽帧。

## 抽样算法

标准化后的总时长为 `T`。当帧数超过上限时，将 `[0, T]` 划分为 `maxFrames` 个整数毫秒区间：

```text
boundary[i] = round(i * T / maxFrames)
boundary[0] = 0
boundary[maxFrames] = T
```

每个区间采用左闭右开语义，并选择区间中点时刻所在的原始帧。输出延时为相邻边界之差。若连续区间选择了同一个原始帧索引，则合并为一帧并累加延时。最后一帧吸收任何整数分配差值，并校验输出延时之和严格等于 `T`。

查找使用单向累计时间游标，整体复杂度为 `O(原始帧数 + 输出帧数)`。相邻合并按原始帧索引判断，不做昂贵的图像内容比较。

## 编辑器动态容量

GIF 从当前帧开始替换时，保留当前帧之前的已有帧。本次导入的上限为：

```ts
const availableFrames = MAX_PROJECT_FRAMES - selectedFrameIndex
```

例如当前选择第 11 帧时，前 10 帧保留，新 GIF 最多抽样为 40 帧。现有 `frameCountAfterReplacement()` 校验继续保留为防御性断言。

## 接入链路

### Works 页面上传

文件经过现有 5MB 校验和 GIF 解码后立即抽样，再将抽样结果转换为 32×16 像素。重新编码的 GIF、可编辑 JSON 和接口 `frameCount` 使用同一组抽样帧。

### 编辑器导入

解码后按动态剩余容量抽样，然后才创建项目帧和像素数据。原有超过 50 帧直接拒绝的行为改为自动抽样。

### 远程作品加载

- 缺少 `editableFileUrl` 时，下载并解码 GIF 后按 50 帧抽样，不再拒绝 51 帧以上的 GIF。
- 存在 `editableFileUrl` 时，旧 JSON 中的超限帧也在 `sanitizeProject()` 前按时间抽样，避免当前 `slice(0, 50)` 缩短时长。
- 若加载时发生抽样，记录该作品需要重新保存；编辑器设备预览前必须先生成并上传合规 GIF。

### 保存和自动保存

`saveOSSOnly()` 在序列化 JSON 和编码 GIF 前再次抽样。JSON、GIF、封面和 `frameCount` 都从同一个输出帧数组生成。该兜底不修改编辑器内的项目对象。

### 导出

GIF 导出不再因历史项目超过 50 帧而直接失败，而是在缩放和编码前抽样。

### 设备预览

- 编辑器预览沿用“有变化先保存”流程，并将“加载时发生过抽样”也视为必须保存的条件。
- Works 列表预览增加帧数防线；已知超过 50 帧或缺少可靠帧数元数据的历史 GIF 不直接下发，提示用户进入编辑器保存一次。
- 预览动作不静默改写历史作品。

## GIF 编码时长

GIF 延时单位为 10ms。现有编码器逐帧执行 `round(delay / 10)`，可能积累舍入误差。编码器改为累计时间量化：先累计毫秒，再计算目标累计厘秒，当前帧写入两次累计值之差。

这样，解码 GIF 的原总时长为 10ms 整数倍时，重新编码后的总时长严格一致；编辑器产生非 10ms 总时长时，只存在 GIF 格式本身允许的整体量化误差，不会逐帧累积。

## 错误与兼容性

- 共享函数的输入错误使用明确异常，由现有上传或编辑器错误展示逻辑接管。
- 不新增依赖，不改变 API 结构。
- 不改变图片/GIF 文件大小和尺寸校验。
- `MAX_PROJECT_FRAMES = 50` 继续作为唯一业务上限。
- 不修改未启用的 `PixelEditor.ts`，只修改当前实际使用的 `PixelEditor.vue`。

## 测试

- 纯函数测试覆盖空输入、非法上限、延时标准化、50 帧边界、100 帧等间隔抽样、可变延时、相邻合并、不可整除总时长、输入不可变和动态容量。
- 编码测试重新解析生成 GIF，验证帧数、每帧延时和总时长。
- Works 契约测试验证抽样位于像素转换前，上传 JSON/GIF/frameCount 共用抽样结果，预览阻止不可靠 GIF。
- 编辑器行为测试验证动态剩余容量、远程 GIF 和旧 JSON 自动抽样、抽样后预览先保存、保存/导出兜底。
- 最后运行全部像素编辑器测试和 QA 构建。

## 非目标

- 不基于画面相似度去重。
- 不修改 GIF 循环次数、颜色量化、缩放或抖动策略。
- 不在 Works 预览动作中自动下载、重编码并覆盖历史作品。
- 不调整每个项目 50 帧以外的其他编辑器容量规则。
